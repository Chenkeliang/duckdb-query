## 前言

每到跨年和月末，财务团队和业务运营都会面临同一个难题：**对账**。

订单系统、支付系统、ERP、银行流水……数据散落在不同的数据库和 Excel 文件中。传统做法要么依赖大数据平台写 Hive SQL 跑批，要么靠人工在 Excel 里 VLOOKUP 逐行比对。前者门槛高、排队慢，后者效率低、容易出错。

我们团队用 AI 辅助开发（Kiro + Claude），在数周内搭建了一个基于 DuckDB 的可视化 SQL 工作台 —— **DuckQuery**。今年跨年期间，它帮助我们在 **20 万笔订单** 中快速定位差异，一条 SQL 就能对出少单、漏单；每月月结时，无论多少份文件需要合并去重，都能通过 SQL 化的方式在几秒内找到问题。

这篇文章分享我们的实战经验，重点讲清楚一件事：**这个项目到底解决了什么问题，以及它是怎么解决的。**

## 一、先说痛点：传统对账到底卡在哪里

在聊解决方案之前，先把问题摊开。

### 1.1 典型的对账场景

一个电商公司的跨年对账，通常涉及这些数据：

| 数据 | 存储位置 | 格式 |
|------|----------|------|
| 订单数据 | MySQL 订单库 | 数据库表 |
| 支付流水 | 银行/支付平台下载 | Excel / CSV |
| ERP 应收 | ERP 系统导出 | Excel |
| 历史归档 | 数据仓库 / 本地文件 | Parquet / CSV |

问题来了：**这些数据分散在不同的系统、不同的格式里，怎么放到一起比对？**

### 1.2 传统方案一：大数据平台

大多数公司的做法是走大数据链路：

```
各业务系统 → ETL 抽数 → 数据仓库（Hive/Spark）→ 写 SQL 跑批 → 产出报表
```

这条路能走通，但有三个致命问题：

**问题 1：T+1 延迟，看不到实时数据**

ETL 通常是每天凌晨跑批，今天只能看到昨天的数据。跨年对账的关键时刻，业务方说"我要看今天的订单差异"，大数据平台给不了。你只能等到明天。

**问题 2：排队等开发**

写 Hive SQL、配 ETL 任务、调度排期……这些都需要数据开发团队支持。跨年和月末恰恰是所有团队都在抢资源的时候，一个对账需求可能排到一周后。

**问题 3：门槛高，业务方用不了**

Hive SQL 的语法、集群的权限、调度平台的操作——这些对财务和运营来说太重了。他们只想知道"哪些订单对不上"。

### 1.3 传统方案二：Excel 手工

另一条路是纯手工：

```
从各系统导出 Excel → VLOOKUP 逐行比对 → 手动标记差异
```

问题更明显：

- **数据量上限**：Excel 超过 10 万行就卡顿，20 万行基本不可用
- **跨源能力为零**：必须先把所有数据导出成 Excel，才能开始比对
- **重复劳动**：每次月结都要重复同样的操作，没有复用性
- **容易出错**：公式写错、行对错、漏筛选……人工操作的风险不可控

### 1.4 核心矛盾

把问题总结成一句话：

> **业务方需要实时、跨数据源的对账能力，但传统方案要么 T+1 延迟（大数据），要么处理不了多源异构数据（Excel）。**

这就是 DuckQuery 要解决的问题。

## 二、DuckQuery 怎么解决这些问题

### 2.1 项目是怎么来的：AI 搭建的全栈分析工具

DuckQuery 并不是一个传统意义上"从零手写"的项目。它的前端（React 18 + TypeScript）、后端（FastAPI + Python）、以及核心的查询引擎（DuckDB），都是在 AI 编程助手的协助下快速迭代出来的。

从需求分析、架构设计、代码实现到 lint 规则和文档规范，AI 参与了整个开发流程。这让一个小团队能在短时间内交付一个功能完整的数据分析工具，而不是等待大数据团队排期。

**这本身就是解决问题的一部分：业务团队不需要依赖大数据团队的排期，AI 帮你快速搭建自己的分析工具。**

`[占位图：DuckQuery 查询工作台全貌 - 左侧数据源面板 + 中间查询编辑器 + 下方结果面板]`

### 2.2 核心能力：实时跨源，不需要 ETL

DuckQuery 解决传统痛点的关键在于两个字：**直连**。

传统大数据方案：
```
MySQL 订单库 → ETL 抽数（T+1）→ 数据仓库 → SQL 查询 → 结果
```

DuckQuery 方案：
```
MySQL 订单库 ← ATTACH 直连（实时）→ DuckDB ← 文件直接查询 → 结果
```

**没有 ETL，没有 T+1，没有排队。** 数据在哪里，就直接查哪里。

这得益于 DuckDB 的两个核心特性：

1. **ATTACH 联邦查询**：通过 DuckDB 的扩展机制，直接挂载 MySQL、PostgreSQL 等外部数据库。不需要导出数据，SQL 直接跨库 JOIN，查的就是源库的实时数据。

2. **文件直接查询**：`read_csv_auto`、`read_parquet` 等函数可以直接用 SQL 查询文件，不需要先导入。Excel 上传后自动转为 DuckDB 原生表，查询性能接近内存数据库。

### 2.3 数据接入：三种方式覆盖所有场景

DuckQuery 的数据源管理页面提供了三个 Tab，覆盖了对账场景的所有数据来源：

**Tab 1 — 文件上传（Upload）**

将银行下载的支付流水 Excel 直接拖拽到浏览器，DuckQuery 自动识别文件格式，推断列类型，生成 DuckDB 原生表。支持 CSV、Excel（多 Sheet 选择）、JSON、Parquet 格式。还支持通过 URL 直接导入远程文件。

`[占位图：数据源管理 - 文件上传 Tab，展示拖拽上传区域 + URL 导入 + 服务器目录导入]`

**Tab 2 — 数据库连接（Database）**

直接连接订单系统的 MySQL 数据库。填写连接信息后，DuckQuery 通过 DuckDB 的 `ATTACH` 机制挂载外部数据库，**无需导出数据，无需 ETL，直接跨库查询实时数据**。

`[占位图：数据源管理 - 数据库连接 Tab，展示 MySQL/PostgreSQL 连接表单 + 已保存连接列表]`

**Tab 3 — 数据粘贴（Paste）**

临时的对账补充数据，比如从邮件或聊天工具中复制的表格片段，直接粘贴即可创建表。智能解析引擎会自动识别分隔符、推断列类型。

`[占位图：数据源管理 - 数据粘贴 Tab，展示粘贴区域 + 智能解析结果预览]`

## 三、实战一：跨年对账，20 万订单实时比对

### 3.1 场景描述

跨年期间，订单系统产生了约 **20 万笔订单**。我们需要将订单系统的数据与支付系统的流水进行比对，找出：

- **少单**：支付系统有流水，但订单系统没有对应记录
- **漏单**：订单系统有记录，但支付系统没有对应流水
- **金额不一致**：两边都有记录，但金额对不上

### 3.2 传统方案需要多久

如果走大数据链路：

1. 提需求给数据团队 → 排期 1-3 天
2. 配置 ETL 从 MySQL 抽数到 Hive → 等 T+1 数据就绪
3. 银行流水 Excel 上传到 HDFS → 需要数据开发协助
4. 写 Hive SQL 跑批 → 大表 JOIN 可能跑 10-30 分钟
5. 结果导出 → 再等

**从提需求到拿到结果，最快也要 2-3 天。跨年高峰期可能更久。**

而且最关键的问题是：**你看到的是 T+1 的数据，不是实时的。** 如果今天下午发现了差异，你无法确认"现在"的状态，只能等明天的数据刷新。

### 3.3 DuckQuery 方案：10 分钟搞定

**Step 1：连接数据源（2 分钟）**

在数据源管理页面：
- 数据库连接 Tab：添加 MySQL 订单库连接，填写 host、端口、用户名密码，点击测试连接
- 文件上传 Tab：拖入银行支付流水 Excel

**Step 2：编写对账 SQL（3 分钟）**

切换到查询工作台的 **SQL Tab**，左侧数据源面板以树形结构展示所有已导入的本地表和已连接的外部数据库表。直接编写：

```sql
-- 跨数据源对账：订单系统（MySQL 实时数据）vs 支付流水（Excel）
-- 联邦查询：mysql_order 是通过 ATTACH 挂载的 MySQL 数据库
SELECT 
    COALESCE(o.order_no, p.order_no) AS order_no,
    o.order_amount,
    p.pay_amount,
    o.order_time,
    p.pay_time,
    CASE 
        WHEN o.order_no IS NULL THEN '少单-订单系统缺失'
        WHEN p.order_no IS NULL THEN '漏单-支付流水缺失'
        WHEN ABS(o.order_amount - p.pay_amount) > 0.01 THEN '金额不一致'
        ELSE '正常'
    END AS diff_type,
    ABS(COALESCE(o.order_amount, 0) - COALESCE(p.pay_amount, 0)) AS diff_amount
FROM mysql_order.orders o
FULL OUTER JOIN payment_flow p 
    ON o.order_no = p.order_no
WHERE o.order_no IS NULL 
   OR p.order_no IS NULL 
   OR ABS(o.order_amount - p.pay_amount) > 0.01
ORDER BY diff_type, order_no
```

这条 SQL 的关键点：

- `mysql_order.orders` — 通过 ATTACH 联邦查询**直接访问 MySQL 中的实时数据**，不是 T+1 的快照
- `payment_flow` — 上传的银行支付流水 Excel，已自动转为 DuckDB 本地表
- `FULL OUTER JOIN` — 全外连接，确保两边的数据都不遗漏
- 一条 SQL 同时完成：少单检测、漏单检测、金额差异检测

**Step 3：执行并查看结果（秒级）**

点击执行，**20 万笔订单的比对，执行时间不到 3 秒**。

`[占位图：查询工作台 - SQL Tab 执行结果，展示差异订单的表格数据，包含 order_no、金额、diff_type 列，底部显示执行耗时]`

结果面板直接展示所有差异订单，按差异类型分类。可以进一步筛选、排序，或导出为 Excel 发给相关方。

### 3.4 关键区别：实时 vs T+1

这里要强调最核心的区别：

| 维度 | 大数据方案 | DuckQuery |
|------|-----------|-----------|
| 数据时效性 | **T+1**（昨天的数据） | **实时**（直连源库） |
| 从需求到结果 | 2-3 天 | 10 分钟 |
| 是否需要 ETL | 是（配置抽数任务） | 否（ATTACH 直连） |
| 是否需要数据团队 | 是（排期等待） | 否（业务自助） |
| 发现差异后能否立即复查 | 不能（等下次 T+1） | 能（再执行一次就是最新数据） |

最后一点尤其重要：**当你发现了 50 笔差异订单，业务方修复了其中 30 笔后，你可以立即重新执行同一条 SQL，确认修复结果。** 不需要等到明天。

这在跨年对账的紧张节奏中，价值是巨大的。

### 3.5 进阶：异步任务处理大批量导出

如果需要将差异结果导出为 Excel 发给相关方，或者查询涉及的数据量特别大，可以切换到 **异步任务** 模式。查询工作台顶部的二级 Tab 提供了"查询模式"和"异步任务"两个入口：

- 提交大查询后，任务在后台执行，不阻塞界面
- 任务完成后可直接下载结果文件
- 支持任务取消和重试

`[占位图：异步任务面板 - 展示任务列表、状态、下载按钮]`

## 四、实战二：月结场景，多文件合并去重

### 4.1 痛点

财务月结时，通常需要处理：

- 来自不同渠道的 **十几份甚至几十份** 对账文件（CSV/Excel）
- 文件格式不完全统一（列名不同、编码不同、列顺序不同）
- 需要合并后去重，找出重复记录和缺失记录

传统方案：要么提交大数据需求等排期（又是 T+1 的问题），要么在 Excel 里手动操作（10 万行以上就卡死）。

### 4.2 DuckDB 的杀手级特性：直接查询文件

DuckDB 有一个让人兴奋的能力：**不需要先导入，就能直接用 SQL 查询文件**。

在 DuckQuery 中，你可以通过服务器目录挂载功能，将存放对账文件的目录直接映射进来。然后利用 DuckDB 的 `read_csv_auto` 和通配符语法，一条 SQL 搞定多文件合并：

```sql
-- 合并当月所有渠道的对账文件（支持通配符批量读取）
SELECT * FROM read_csv_auto('/data/reconciliation/2026-01/*.csv', 
    union_by_name = true,    -- 按列名合并，容忍列顺序不同
    filename = true           -- 自动添加来源文件名列
)
```

`union_by_name = true` 是关键参数 —— 即使不同文件的列顺序不一样，甚至某些文件多了或少了某些列，DuckDB 也能按列名智能对齐合并。`filename = true` 会自动添加一列标记每行数据来自哪个文件，方便追溯。

### 4.3 去重与差异分析

合并后，用 SQL 进行去重和差异分析：

```sql
-- Step 1: 合并所有文件并去重
WITH all_records AS (
    SELECT *, filename 
    FROM read_csv_auto('/data/reconciliation/2026-01/*.csv', 
        union_by_name = true, filename = true)
),
-- Step 2: 标记重复
duplicates AS (
    SELECT order_no, COUNT(*) AS cnt, 
           STRING_AGG(DISTINCT filename, ', ') AS sources
    FROM all_records
    GROUP BY order_no
    HAVING COUNT(*) > 1
)
-- Step 3: 输出重复记录及来源
SELECT d.order_no, d.cnt AS duplicate_count, d.sources,
       a.amount, a.status
FROM duplicates d
JOIN all_records a ON d.order_no = a.order_no
ORDER BY d.cnt DESC, d.order_no
```

### 4.4 可视化辅助：不写 SQL 也能操作

查询工作台提供了四个查询模式 Tab，对于不熟悉 SQL 的财务同事，其他 Tab 同样能完成这些操作：

| Tab | 功能 | 适用场景 |
|-----|------|----------|
| **SQL** | 自由编写 SQL | 复杂对账逻辑、自定义分析 |
| **JOIN** | 可视化连接查询 | 快速关联两张表，选字段、选关联条件 |
| **SET** | 集合操作（UNION/INTERSECT/EXCEPT） | 合并、去重、差集 |
| **Pivot** | 透视表 | 汇总统计 |

**SET Tab** 特别适合月结场景：选择两张表，一键执行 EXCEPT（差集），直接找出"A 系统有但 B 系统没有"的记录，不需要写一行 SQL。

`[占位图：查询工作台 - SET Tab，展示两张表的集合操作配置界面]`

**JOIN Tab** 适合快速关联比对：可视化选择两张表和关联字段，自动生成 JOIN SQL。

## 五、总结：这个项目到底解决了什么

把前面的内容收拢，DuckQuery 解决的核心问题可以用一张表说清楚：

| 痛点 | 传统方案 | DuckQuery 怎么解决 |
|------|---------|-------------------|
| 多数据源分散，无法统一查询 | 需要 ETL 抽数到数据仓库 | ATTACH 联邦查询，直连源库 |
| T+1 延迟，看不到实时数据 | 等每天凌晨跑批 | 直连源库，查的就是实时数据 |
| 依赖数据团队排期 | 提需求、等开发、等上线 | 业务自助，10 分钟出结果 |
| Excel 处理不了大数据量 | 超过 10 万行就卡死 | DuckDB 列式引擎，20 万行秒级 |
| 多文件格式不统一 | 手动对齐列名、合并 | `union_by_name` 智能按列名合并 |
| 每次月结重复劳动 | 重新做一遍 VLOOKUP | SQL 保存复用，下次直接执行 |
| 搭建分析工具周期长 | 数月开发 | AI 辅助，数周交付 |

### DuckDB 的核心特性总结

| 特性 | 对账场景的价值 |
|------|---------------|
| **嵌入式部署** | 不需要搭建集群，Docker 一键启动 |
| **列式存储 + 向量化执行** | 20 万行数据秒级查询 |
| **直接查询文件** | `read_csv_auto`、`read_parquet` 无需导入 |
| **通配符批量读取** | `*.csv` 一次读取整个目录的文件 |
| **union_by_name** | 不同格式的文件按列名智能合并 |
| **ATTACH 联邦查询** | 直连 MySQL/PostgreSQL，跨库 JOIN，实时数据 |
| **内存限制可控** | 不会撑爆服务器 |

### AI 辅助开发的价值

这个项目本身就是 AI 辅助开发的产物。从需求到交付，AI 参与了每一个环节：

- **需求转代码的速度**：一个 spec 文档描述清楚需求，AI 就能生成完整的前后端代码
- **规范一致性**：通过 steering 规则和 lint 规则，AI 生成的代码自动遵循项目规范
- **快速迭代**：发现问题后，描述清楚就能修复，不需要等排期

这意味着：**业务团队不需要依赖大数据团队的排期，AI 帮你快速搭建自己的分析工具，然后用这个工具实时解决对账问题。**

## 六、实操指南：从零开始

### Step 1：启动 DuckQuery

```bash
git clone https://github.com/Chenkeliang/duckdb-query.git
cd duckdb-query
./quick-start.sh
```

打开 `http://localhost:3000`。

### Step 2：导入数据

1. 进入 **数据源管理** 页面
2. 在 **文件上传 Tab** 拖入支付流水 Excel
3. 在 **数据库连接 Tab** 添加订单系统 MySQL 连接
4. （可选）在 **数据粘贴 Tab** 粘贴补充数据

### Step 3：执行对账查询

1. 切换到 **查询工作台**
2. 左侧数据源面板确认数据已就绪
3. 在 **SQL Tab** 编写对账 SQL（参考上文示例）
4. 点击执行，结果面板实时展示差异数据

### Step 4：导出结果

- 结果面板支持导出为 CSV/Excel
- 大数据量可使用异步任务模式，后台执行后下载
